title: Claude Code
description: What Cardea sets up inside Claude Code, and what it leaves alone.

Claude Code keeps its own state next to its settings: sessions, plugin caches, and the list
of MCP servers. Cardea therefore never links a whole folder. It owns a few named things and
leaves everything else to you.

## What Cardea owns

| Thing | Where it lives | How it gets there |
|---|---|---|
| Global rules | `~/.claude/CLAUDE.md` | Symlink to `claude/CLAUDE.md` |
| tldr skill | `~/.claude/skills/tldr/` | Symlink to `claude/skills/tldr/` |
| baby skill | `~/.claude/skills/baby/` | Symlink to `claude/skills/baby/` |
| MCP servers | User scope in `~/.claude.json` | `claude mcp add-json --scope user` |
| <Tool icon="plannotator.png">Plannotator</Tool> | Plugin, plus the `plannotator` binary | Plugin marketplace, binary installer |
| <Tool icon="langfuse.svg">Langfuse tracing</Tool> | Plugin | Plugin marketplace, configured from `.env` |
| <Tool icon="claude.svg" mono>Cardea plugin</Tool> | Plugin, a copy in `~/.claude/plugins/cache/` | `claude plugin install` from the repo |
| Five more plugins | Plugins | Their own marketplaces |
| <Tool icon="herdr.svg">herdr</Tool>, graphify and marimo skills | `~/.claude/skills/herdr/`, `~/.claude/skills/graphify/`, `~/.claude/skills/marimo-notebook/` | `scripts/vendor-skills.sh` |

## What Cardea leaves alone

- `~/.claude/settings.json`: your hooks, permissions and preferences.
- Your other skills in `~/.claude/skills/`, and any other plugins.
- MCP servers with names Cardea does not use.

## MCP servers

Registered at user scope, so every project gets them. Each run removes and re-adds them,
which keeps them in line with the script.

| Name | What it does | Command |
|---|---|---|
| <Tool icon="serena.png">`serena`</Tool> | Understands code by symbol, not by text | `uvx --from git+…/serena@v2.1.0 serena start-mcp-server --context claude-code --project-from-cwd` |
| <Tool icon="xcode.svg" mono>`xcodebuild`</Tool> | Builds, tests and runs iOS apps | `npx -y xcodebuildmcp@2.7.0 mcp` |
| <Tool icon="swift.svg" mono>`swiftlens`</Tool> | Swift symbol lookups | `uvx swiftlens@0.2.14` |
| <Tool icon="xcode.svg" mono>`xcode`</Tool> | Apple's bridge into a running Xcode | `xcrun mcpbridge` |
| <Tool icon="container-use.png">`container-use`</Tool> | One container and git branch per agent | `container-use stdio` |
| <Tool icon="basic-memory.png">`basic-memory`</Tool> | Durable notes on the NAS | HTTP, the URL from `.env` |

Values come from `.env` when the script runs. After changing `.env`, run the script again.

The Xcode bridge only connects while Xcode is open, so Claude Code reports it as failed the
rest of the time. That is expected.

## Plugins

**Plannotator** opens plans in a review UI before Claude acts on them. The plugin only adds
hooks; those hooks call the `plannotator` binary, which the script installs on its own at a
pinned version.

**Langfuse** sends each turn to Langfuse after it finishes: your prompt, Claude's reply,
every tool call, and timing, grouped by session. The script always points it at the NAS, even
before there are keys, so it never falls back to Langfuse's hosted service. The secret key is
passed on standard input, kept out of the process list, and stored in the macOS keychain.

## The Cardea plugin

Cardea's own skills and agents ship as a Claude Code plugin. Skills load when a task calls
for them, so unlike the rules in `CLAUDE.md` they cost nothing until they are used.

| For | Skills |
|---|---|
| The self-hosted stack | `basic-memory`, `langfuse`, `obsidian`, `plannotator`, `serena`, `graphify` |
| Looking things up | `retrieval-order` |
| iOS | `driving-ios-simulator-with-axe`, `rendering-swiftui-previews`, `sim-clone-restore`, `grdb` |
| Reviews and releases | `panel`, `comment-audit`, `pre-commit-audit`, `semantic-commit`, `local-merge`, `post-merge-sweep`, `release-changelog` |
| Recommendations | `recsys` |

`retrieval-order` sets where an agent looks before it asks: the session, then the rules and
memory, Basic Memory, the active plan, graphify, Serena and the code, git history, tests and
builds, skills and offline docs, the web, and you last. Notes and history answer why
something is the way it is; the code and live results answer what it is now, and win when a
note is out of date.

Three agents make up the design panel: a UX designer, the average chud and a power user. The
`panel` skill puts a question to all three at once and merges their verdicts into one
recommendation.

`install.sh` installs the plugin from your checkout. Claude Code keeps its own copy, in
`~/.claude/plugins/cache/cardea/cardea/<version>/`, so an edit in the repo does nothing until
you refresh that copy and start a new session. Rerunning `./install.sh` updates the Cardea
plugin and every marketplace plugin. For a quick refresh after an edit, update just this one:

```sh
claude plugin update cardea@cardea
```

The repo is private, so installing the plugin anywhere else needs access to it. With access:

```sh
claude plugin marketplace add yuzuholic/cardea
claude plugin install cardea@cardea
```

## Orchestrator and implementer

For a job with several parts, the plugin has two more agents. The orchestrator plans and
checks; implementers make the changes. The orchestrator never writes feature or bug-fix code,
only quick one-off edits such as a convention or a note, and an implementer never starts
another agent. Both edit files with the Edit and Write tools, never with scripts.

| Agent | Started by | Model | Effort |
|---|---|---|---|
| `cardea:orchestrator` | you | Opus 5.5 | medium |
| `cardea:implementer` | you | Opus 5.5 | medium |
| `cardea:implementer` | the orchestrator | Sonnet 5.5 | low |

Start either one with its effort spelled out:

```sh
claude --agent cardea:orchestrator --effort medium
claude --agent cardea:implementer --effort medium
```

The orchestrator reads the code (starting from the graphify map when the repo has one) and
splits the work into tasks one implementer can finish alone, at most five at once. A plan with
two or more implementers opens in Plannotator for your approval; a single task starts straight
away. Each implementer gets a brief with the goal, the files, the limits and the check that
proves it worked. It makes the change, runs the check and reports what it changed, what it
checked and what it left.

The orchestrator never waits on an implementer in the foreground, so it can answer you while
they work. A task that changes files alongside others, or builds an app, gets its own git
worktree and branch; read-only tasks and a lone small change run in your checkout.
Every task gets a time budget, shown as minutes and a due time (for example "25 min, due
16:40") in the plan and the brief, and the background wait that tracks the implementer is armed
with it as its timeout. On an overrun the orchestrator investigates before acting. An
implementer waiting on a prompt goes to you. One still producing output gets a single extension
of half its budget and a one-line note to you. One with no new output, or any second overrun,
is stopped and reported to you with its last output, and you decide. Outside herdr it cannot
look inside a running subagent, so an overrun goes straight to you. Each batch's final report
lists budget against actual time per task, and the orchestrator appends those rows to the Basic
Memory note `plans/<Project> Task Time Estimates.md` (the last 50 tasks, plus rules of thumb by
kind of task) and reads it when planning. Cardea has no Basic Memory project, so for cardea the
report is the only record.
An implementer that is blocked or needs something comes first: at the start of every turn the
orchestrator checks implementer messages and pane states and resolves any blocker before other
topics, and a blocker that needs you leads its reply. A permission denial goes to you, with the
options of adding an allow rule for that exact command or approving it in the implementer's own
tab. The orchestrator never runs the denied command itself, and never answers an approval or
permission prompt for you. When a command depends on an allow rule, the brief gives its exact
allow-listed spelling, and a denied implementer reports the denial verbatim instead of retrying
with another spelling or tool.
Implementers stage their work and never commit. The orchestrator reviews each one, then lands
it in your checkout as uncommitted changes, one at a time in the order they finish, under a
per-repo lock that also keeps orchestrators in other sessions from landing at the same time.
If a change no longer applies, or its check fails in your checkout, it stops and asks you.
After landing, it removes the worktree, its build data, the branch, the tab and any simulator
clone the task made. Saying `close impl-<task>` does the same at any time. When the batch is
done and any task used a simulator, it deletes unavailable simulators and reports the disk space
freed. It also refreshes the graphify map. Once the work is merged to main, it runs the
`post-merge-sweep` skill, which also clears what crashed or restarted sessions left behind.

**Inside herdr**, every implementer gets a tab of its own in your workspace, named
`impl-<task>`, so you can watch it work and step in. The orchestrator opens the tab without
taking your focus, starts the implementer in it, sends the brief and reads the result back. If
an implementer stops on a question (trusting a folder, a permission, anything else), the
orchestrator asks you; it never answers for you.

**Outside herdr**, it starts implementers as ordinary background subagents instead, on Sonnet
at low effort.

## Hooks

The plugin also ships four hooks. Two can block a tool call, and the commit hook can also ask
you first; the other two only add a note. If a hook fails for any reason, the call goes
ahead. None of them ever approves a call, so your usual permission prompts still apply.

| Hook | When | What it does |
|---|---|---|
| Session note | A session starts, resumes or is compacted | Reminds Claude of the lookup order, names the repo's Basic Memory project (the repo's folder name), says whether a graphify map exists, and lists up to five notes from the last week. If the NAS doesn't answer within 1.5 seconds, the notes are left out. |
| Secrets | Before reading, searching, editing or running a command | Blocks `.env` files and private keys (`id_rsa`, `*.pem`, `*.key`, `*.p12`, `*.p8`), saying secrets go through environment variables only. `.env.example`, `.sample` and `.template` files and `*.pub` keys are fine. |
| Commit message | Before a `git` command | Blocks a commit whose message isn't `<type>: <subject>`: lowercase, no full stop, under 72 characters, no body and no trailers such as `Co-Authored-By`. It lists what's wrong. If the message can't be read, for example because an editor opens, the commit goes ahead. Outside the cardea repo, it also checks the message and the lines being committed for any mention of an AI tool or company, and asks you to approve that one commit when it finds one, listing each file, line and word. Every commit is asked fresh. |
| Web nudge | The first web search or fetch in a session | Reminds Claude to check notes, code and history first. It never blocks. |

The secrets check on commands is a scan of the words in the command, so it misses some
routes: a variable holding the path, `git show HEAD:.env`, or `grep -r` across a folder. It
stops accidents, not someone trying to get round it.

## Marketplace plugins

The script installs these from their own marketplaces. On a rerun it switches back on any
that were turned off and updates each one.

| Plugin | What it adds |
|---|---|
| [superpowers](https://github.com/obra/superpowers-marketplace) | Working habits: brainstorming, plans, TDD, systematic debugging, code review |
| [ponytail](https://github.com/DietrichGebert/ponytail) | Pushes toward the simplest solution that works |
| [apple-skills](https://github.com/Prisma-Labs-Dev/apple-skills) | Apple API references: SwiftUI, UIKit, SwiftData and more |
| [cloudflare](https://github.com/cloudflare/skills) | Guidance for building on Cloudflare |
| [humanizer](https://github.com/blader/humanizer) | Rewrites text that reads as machine-written |

herdr and graphify each ship a skill of their own. `scripts/vendor-skills.sh` generates both
from the installed versions on every run, so they always match. graphify's installer would
also edit `CLAUDE.md`; the script runs it against a scratch folder so the real one is never
touched. marimo publishes its skills in a git repo, so the script copies the `marimo-notebook`
skill from the latest `marimo-team/skills`.

## Decisions you make

When a decision is yours to make, Claude asks in the chat, one question at a time, following
the rules in `claude/CLAUDE.md`:

1. It explains the problem simply and lists the questions coming.
2. Each question comes as "Q1 of 3". It says what it decides in a sentence or two, then shows a
   table of options with short cells for what is good and not good about each. One is marked
   **(recommended)**. A one-line pick gives the reason and names the cheapest option that has no
   real downside. Jargon is explained in brackets, and side notes come last.
3. It confirms your answer in one line and waits for "next". "Go with yours" accepts the
   recommendation.
4. At the end it sums up every decision and waits for your go before acting.
5. Each decision is saved to Basic Memory.

Choices with an obvious default don't get a question; Claude goes ahead and mentions it in
one line.

## Your subscription, not an API key

Claude Code uses your Claude subscription login. If `ANTHROPIC_API_KEY` is set in your shell,
Claude Code uses that instead and bills the API. `./install.sh --check` warns when it is set.
