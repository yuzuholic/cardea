The whole stack runs on TrueNAS as one service, `cardea`. Its image, `yuzuholic/cardea`, is a
launcher: it carries the stack's compose file and a current Docker Compose, and starts each
service from its official image, next to itself, on the NAS's own Docker. Stopping `cardea`
stops the whole stack.

On the NAS it lives at `/mnt/main/Docker/lab`; over SMB it shows up as
`/Volumes/Docker/lab`. That folder holds two things: `compose.yml` (from `nas/` in the
repo), which declares every setting the stack reads; and `.env`, which holds their values.

```sh
cd /mnt/main/Docker/lab
sudo docker compose up -d
sudo docker compose logs -f cardea
```

`truenas_admin` is not in the docker group, so `docker` needs `sudo`. Put `sudo` on the
`docker` call itself: `sudo cd` fails, because `cd` is built into the shell.

<Callout type="warn" title="cardea controls Docker on the NAS">
  To start the services, `cardea` talks to the NAS's Docker through its socket. Anything with
  that access can do anything to the NAS, so only run an image you trust: the published
  `yuzuholic/cardea`, or one you built from this repo.
</Callout>

## The image

[`yuzuholic/cardea`](https://hub.docker.com/r/yuzuholic/cardea) is on Docker Hub for x86 and
Arm (`linux/amd64` and `linux/arm64`). `:latest` follows the newest build, which is
`:0.2.0` today; `:0.1.0` was the first release.

## Changing the stack

The services are defined in `nas/lab/docker-compose.yml`, which is built into the image.
Change it there, then build and push the image. The NAS is x86 and the Mac is Arm, so build
for both:

```sh
docker buildx build --platform linux/amd64,linux/arm64 -t yuzuholic/cardea:latest --push nas/
```

Watchtower on the NAS picks up a new `:latest` by itself, which briefly restarts the whole
stack. To choose when an update lands, set a release tag such as `:0.2.0` in `compose.yml`
instead, and change it when you want the next one.

After changing `.env`, run `sudo docker compose up -d`. It sees the new values, recreates
`cardea`, and `cardea` applies them to the stack. `restart` is not enough: it reuses the old
container with the old values.

The services keep the project name `lab`, so their containers and volumes keep their old
`lab_` names. That is also why Portainer shows two stacks: `cardea`, which is only the
launcher, and `lab`, the services it starts. To use a different project name or notes folder, set `CARDEA_PROJECT` or
`CARDEA_KB` on the `cardea` service.

## Moving from the old stack

The stack used to run straight from `docker-compose.yml` on the NAS. To switch, in
`/mnt/main/Docker/lab`:

1. `sudo docker compose down` stops the old stack. Volumes are kept, so no data is lost.
2. Move the old `docker-compose.yml` out of the folder.
3. Add `compose.yml`, and `.env` filled in from `nas/.env.example`.
4. `sudo docker compose up -d`, then `sudo docker compose logs -f cardea` to watch it start.

## Who can reach what

| Service | Port | Reachable from |
|---|---|---|
| Hindsight | 8888 | LAN |
| Hindsight control plane | 9999 | The NAS itself only |
| Langfuse web | 3000 | LAN |
| MinIO | 9090 | LAN |
| ClickHouse, Postgres, Hindsight's Postgres, Redis, Langfuse worker | — | The NAS itself only |

Portainer lists ports like `5432:5432` without showing that they are bound to the NAS's own
loopback address. They are not open to the network.

**Hindsight's REST API has no login either.** Its MCP endpoint wants `HINDSIGHT_MCP_TOKEN` as a
bearer token, but the rest of port 8888 does not, so keep it on the LAN too.

**MinIO's 9090 has to stay on the LAN**, because your browser uploads Langfuse media straight
to it. That is why the media addresses point at `truenas.local` and not `localhost`.

The repo defaults use `truenas.local`; `nas.local` does not exist on this network. For the
Mac's own settings, see [Use a fixed address](#use-a-fixed-address).

## Use a fixed address

`.local` names resolve over mDNS, which stalls for 2-4 s now and then. Every Hindsight and
Langfuse call pays for that. Measured by name, calls spiked to 2-4 s; by IP, 0.24 s at most.

Only the Mac's `NAS_URL` and `LANGFUSE_HOST` matter for speed. Set them to the
NAS's fixed IP or a router DNS name in your own `.env`, never in the repo. `./install.sh`
and `./install.sh --check` warn about any `.local` address. `NEXTAUTH_URL`, the S3
endpoints are only used by the browser, so they can stay as they are.

## Secrets

They live in `.env` beside `compose.yml` on the NAS, never in the repo.
`nas/.env.example` lists every one. Every secret is required: if one is missing,
`sudo docker compose up` stops and names it, instead of quietly starting a service with an
empty password.

The Cloudflare tunnel is optional. It only starts when `CLOUDFLARE_TUNNEL_TOKEN` is set.

Langfuse telemetry is off.

Generate them as hex, not base64. The Postgres password ends up inside a web address, and
base64's `+`, `/` and `=` would break it.

```sh
openssl rand -hex 24   # passwords and secrets
openssl rand -hex 32   # ENCRYPTION_KEY
```

Values that have to match are filled in for you: the Postgres address uses
`POSTGRES_PASSWORD`, and Langfuse's three storage keys use `MINIO_ROOT_PASSWORD`. Set them
by hand only if you want them to differ.

Changing `ENCRYPTION_KEY` once Langfuse holds data makes that data unreadable, so do it early
or not at all.

`NEXTAUTH_URL` must be the address you open Langfuse at in the browser, or signing in
redirects you somewhere dead. It defaults to `http://truenas.local:3000`.

## Langfuse

Open `http://truenas.local:3000` and sign up; the first account becomes the admin. Then
create an organisation and a project, and under **Settings → API Keys** create a key pair.
The secret key is shown once.

Once your account exists, turn off sign-ups: set `AUTH_DISABLE_SIGNUP=true` in the NAS
`.env` and run `sudo docker compose up -d`.

The first request after Langfuse starts can take around 30 seconds. After that it answers
straight away.

Next.js inside the container listens on whatever `HOSTNAME` says, and Docker sets that to the
container's ID. The compose file forces `HOSTNAME: "0.0.0.0"`; without it, port 3000 never
answers.

## Hindsight

Hindsight is long-term memory: agents retain what happened and recall it later. It runs as
`hindsight` beside its own Postgres with pgvector, `hindsight-db`, so Langfuse's database is
untouched. Embeddings run inside the container; only fact extraction calls a model, and it
does so through the `claude` CLI on your Claude subscription, with no API key, using a token
from `claude setup-token`. `HINDSIGHT_LLM_MODEL` is optional and defaults to `claude-haiku-4-5`.

Setting `DEEPSEEK_API_KEY` adds DeepSeek (`deepseek-v4-flash`) as a second model: when a call to
Claude fails after its retries, Hindsight tries DeepSeek. Without it, nothing changes.

Setting `HINDSIGHT_LANGFUSE_AUTH` (base64 of a Langfuse project's `public:secret` key pair) sends
Hindsight's own traces to Langfuse under the environment `hindsight`: retain, recall,
consolidation, and each model call with its tokens. They are not linked to the Claude Code
session that called Hindsight.

The audit log keeps every recall (the query and the memories returned) and retain (the content
sent) in the `audit_log` table of `hindsight-db`, forever. Read-only tools such as
`list_memories` are not logged. For example, the last 20 calls:

```sh
sudo docker exec hindsight-db psql -U hindsight -c \
  "select action, started_at, request->>'query' as query from audit_log order by started_at desc limit 20"
```

One-time setup:

1. On the Mac, or any machine logged in to the subscription, run `claude setup-token`.
2. Put the token in the NAS `.env` as `CLAUDE_CODE_OAUTH_TOKEN`.
3. Run `sudo docker compose up -d`.

The token lasts about a year; renew it yearly by repeating steps 1 and 2.

`HINDSIGHT_DB_PASSWORD`, `HINDSIGHT_MCP_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` are required. Put the same token in the Mac's `.env` as `HINDSIGHT_MCP_TOKEN`,
and `install.sh` registers the `hindsight` MCP server. All projects share one bank, `cardea`.

Fact extraction counts against the subscription's usage limits. Upstream supports this
provider on linux/amd64 only and calls it unsuitable for shared or production deployments.

## The vault

The notes are plain Obsidian markdown on the NAS, at `/Volumes/NAS/Vault` on the Mac. No
server watches the folder: you read it in Obsidian, and agents edit the same files directly.
Each project is one title-cased folder (`Aletheia/`, `Homelab/`, `System/`). How pages are
laid out and written is in the `obsidian` skill. Durable decisions and preferences go to
Hindsight instead.

## Backups

None. Langfuse has no high availability either. What matters is the
`langfuse_postgres_data` and `langfuse_clickhouse_data` volumes.

## Pins

Upstream Langfuse floats `langfuse:4`, `postgres:17` and `redis:7`, and ships MinIO with no
tag. Here all four are exact. MinIO is pinned by digest, because Chainguard publishes no
version tags on its free tier; if that digest stops pulling, look up
`cgr.dev/chainguard/minio:latest` again and update it.
